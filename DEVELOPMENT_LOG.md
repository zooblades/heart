# Heartbound: журнал разработки

Этот файл ведёт историю изменений по патчам (коммитам) и текущее состояние проекта.
**Правило: после каждого патча добавляется запись в раздел «История патчей» (внизу, новая запись сверху списка новых).**
Дополняет `AI_TASKS.md` (правила для ИИ-агентов), `OVERVIEW.md` (числа и механики) и планы развития.

Что здесь считается «проверено»:
- **Сборка (CI)**: GitHub Actions собирает Fabric и NeoForge и гоняет юнит-тесты чистой логики.
- **В игре**: проверяет только владелец проекта. Если не сказано иначе, функция «в игре не проверена».
- Последняя успешная сборка CI на момент записи: коммит `3f773a1` (2026-10-08), оба загрузчика, 67 юнит-тестов.

### Известные ограничения и непроверенное
- Всё, что помечено «нет» в столбце «И», в игре не проверялось.
- Жители и пиглины двигаются через «мозг» (WALK_TARGET), у них следование, дом и занятия менее плавные. Дальнейшая работа по плану (этап 7) строится вокруг жителей.
- Записи об умерших мобах чистятся только для партнёров; данные симпатии остаются.
- Паузы, лимиты разговоров и настроения хранятся в памяти (после перезапуска сбрасываются).
- Версии загрузчиков взяты из шаблона (Fabric API 0.109.0, NeoForge 21.1.80), не самые свежие.
- `OVERVIEW.md` не описывает дневник, память событий и остановку моба: он актуален на коммит `0a894c7`.
- Пол мобов определяется по UUID и **не хранится**. План (этап 7) предполагает пол, сохраняемый в данных сущности и меняемый: это архитектурное изменение, его нужно согласовать до реализации.
- Ключ хранения симпатии (`AffinityTable.Key`) это пара «моб, игрок». Для отношений игрок ↔ игрок (этап 6) его придётся обобщить; об этом нужно будет сначала составить план.

## 5. Правила, которые важно помнить (из `AI_TASKS.md` и плана)

- Сначала изучить существующий код, не переписывать работающее, не ломать Fabric и NeoForge.
- Не придумывать новые механики без согласования; идеи предлагать отдельно.
- Не считать функцию готовой без проверки; не выдумывать уже существующие механики и тесты.
- Если нужны архитектурные изменения, сначала объяснить их владельцу.
- Не переходить к следующему крупному этапу, пока предыдущий не работает стабильно.
- Отправка в GitHub: владелец разрешил Claude (чату) **всегда пушить изменения без отдельного запроса** (это разрешение для работы в этом чате и не отменяет правило `AI_TASKS.md` для других агентов).
- Рамки содержания: все персонажи в романтике взрослые, романтика мягкая (намёки и затемнение), без откровенного; согласие мобов моделируется шансом, настроением и обидой.
