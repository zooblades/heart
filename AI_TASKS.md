# AI_TASKS.md — Heartbound

## 1. Информация о проекте

**Название:** Heartbound  
**Игра:** Minecraft Java Edition  
**Тип проекта:** Minecraft-мод  
**Репозиторий:** GitHub  
**Основной язык:** Java (если проект использует другой язык или дополнительные технологии, сначала проверь существующую структуру).

Проект разрабатывается с помощью нескольких ИИ-агентов, например Claude и OpenAI Codex. Они должны иметь возможность продолжать работу друг за другом.

## 2. Главная цель

Создать полноценный, стабильный и качественный Minecraft-мод Heartbound на основе требований владельца проекта.

Не ограничивайся демонстрационным прототипом. Реализуй запрошенные механики так, чтобы они действительно работали в игре.

Перед началом работы изучи существующий проект. Не создавай новый проект поверх старого и не удаляй уже реализованные функции без необходимости.

## 3. Обязательные правила для ИИ

1. Всегда изучай структуру проекта перед внесением изменений.
2. Проверяй README.md, build.gradle или build.gradle.kts, gradle.properties, настройки загрузчика и существующий код.
3. Не меняй версию Minecraft, Java, Forge, NeoForge или Fabric без согласования с владельцем проекта.
4. Не переписывай весь проект ради добавления одной функции.
5. Сохраняй совместимость с уже реализованными механиками.
6. Пиши рабочий код, а не псевдокод, заглушки или комментарии вместо реализации.
7. Не утверждай, что функция готова, если она не реализована или не проверена.
8. Используй существующие системы регистрации предметов, блоков, сущностей, событий и ресурсов, если они уже есть в проекте.
9. Соблюдай соглашения об именовании и стиль кода, используемые в проекте.
10. Не удаляй пользовательские изменения и не выполняй опасные Git-команды без разрешения.
11. Не добавляй ненужные зависимости.
12. При необходимости создавай и изменяй текстуры, модели, рецепты, локализации и другие ресурсы мода.
13. Не придумывай новые игровые механики самостоятельно, если они могут изменить задумку владельца. Предлагай идеи отдельно.
14. Если информации недостаточно для безопасного изменения архитектуры, сначала задай вопрос или изучи код.
15. Все изменения должны быть понятны следующему ИИ-агенту.

## 4. Порядок работы

Перед каждой задачей:

1. Изучи текущий код и последние изменения Git.
2. Прочитай этот файл и README.md.
3. Определи, какие файлы необходимо изменить.
4. Проверь, не реализована ли нужная функция уже.
5. Выполни задачу минимальными необходимыми изменениями.
6. Проверь код на ошибки.
7. Запусти подходящие проверки и сборку Gradle, если среда позволяет.
8. Исправь обнаруженные ошибки, относящиеся к твоим изменениям.
9. Обнови документацию и этот файл.
10. Подготовь отчёт для следующего ИИ-агента.

Не останавливайся после простого создания файлов, если задачу можно полностью реализовать и проверить.

## 5. Текущий статус проекта

**Статус:** требует проверки текущего состояния репозитория.

**Версия Minecraft:** определить по файлам проекта.

**Загрузчик модов:** определить по файлам проекта (Forge, NeoForge, Fabric или другой).

**Версия Java:** определить по настройкам проекта.

**Реализованные функции:** перечислить после изучения существующего кода.

**Незавершённые функции:** определить после изучения существующего кода.

**Известные ошибки:** записать подтверждённые ошибки.

**Последняя успешно проверенная сборка:** указать результат и дату, если известны.

Не отмечай функции как готовые только на основании того, что их файлы существуют.

## 7. Как работать с GitHub

- Работай в текущем репозитории и согласованной ветке.
- Перед изменениями проверь `git status`.
- Не перезаписывай чужие незакоммиченные изменения.
- Не выполняй принудительный сброс истории, удаление веток или принудительную отправку изменений без разрешения.
- Делай небольшие логически завершённые изменения.
- Перед коммитом проверь список изменённых файлов.
- Не включай в коммиты секреты, токены, пароли и локальные файлы с конфиденциальными данными.
- Не создавай коммит и не отправляй изменения на GitHub без разрешения, если владелец проекта явно не поручил это.

Если обнаружен конфликт Git, не удаляй изменения автоматически. Сначала выясни, какие версии файлов содержат нужную работу.

## 9. Критерии готовности задачи

Задача считается выполненной, когда:

- [ ] Реализация соответствует требованиям владельца.
- [ ] Код интегрирован с существующим проектом.
- [ ] Нет известных ошибок, вызванных изменениями.
- [ ] Выполнены доступные релевантные проверки.
- [ ] Результат сборки указан честно.
- [ ] Документация и статус обновлены.
- [ ] Следующий агент может продолжить работу без повторного исследования всей задачи.

Если сборка не запускалась, укажи это прямо. Если сборка не прошла из-за существующей проблемы, не скрывай ошибку.

## 10. Основной принцип

**Главная цель — последовательно развивать один и тот же проект Heartbound, сохраняя весь предыдущий прогресс.**

Каждый ИИ-агент отвечает не только за написание кода, но и за аккуратную передачу работы следующему агенту.

Не начинай заново то, что уже работает. Не выдавай предположения за факты. Не жертвуй стабильностью проекта ради скорости.
